# 01 接入与冻结

对应实验脚本第 1、2 段，证据前缀 `01-onboard-*`、`02-freeze-*`。

## 一、接入：PNG 字节如何成为素材

### 1.1 合法上传

```sh
PUT /v1/assets/asset-a        # 请求体就是 PNG 字节，不是 JSON
```

服务先做 PNG 解码与尺寸校验（1..1024 像素、≤2 MiB），通过后记录 sha256 摘要，
状态置为 `available`。实际响应（`01-onboard-put-asset-a-201.json`）：

```json
{
  "id": "asset-a",
  "digest": "fce5d44a93777695889c03941c61d7517cce82a1dc766bb2734bd2b353fe3c2d",
  "state": "available",
  "width": 16, "height": 16, "png": "……base64……"
}
```

**来源核对**：响应里的 `digest` 必须等于本地 `sha256sum training/assets/asset-a.png`。
这是整条信任链的起点——后面所有"字节一致"的断言都回溯到这个摘要。

### 1.2 入口校验拒绝什么

| 尝试 | 结果 | 证据 |
|---|---|---|
| 上传 `bad-not-png.bin`（纯文本） | **400 invalid**：`invalid PNG: png: invalid format: not a PNG file` | `put-bad-bytes-400.json` |
| 同 ID 同字节再传一次 | **201 幂等**，返回同一条记录，摘要不变 | `put-same-bytes-idempotent-201.json` |
| 同 ID 传不同字节（asset-b 的内容） | **409 conflict**：`asset id already exists` | `put-different-bytes-409.json` |
| 场景引用不存在的 `asset-ghost` | **409 conflict**：`scene references unavailable asset` | `scene-references-missing-asset-409.json` |

关键规则（来自服务行为，可在 `internal/service/assets.go` 与 `scenes.go` 核对）：

- 素材 ID 是内容的稳定身份；**相同 ID 不能替换为不同内容**，内容只能在 `available` 状态下原样重传。
- 场景保存与快照冻结都在同一事务里检查引用闭包，悬空引用无法落地。

### 1.3 场景落地

```sh
PUT /v1/scenes/emblem   {"name":"退役训练-印记","expectedRevision":0,"document":{……}}
```

返回 `revision: 1, state: active`（`01-onboard-put-scene-emblem-rev1.json`）。
乐观修订号从 1 开始，之后每次有效转换 +1。

## 二、冻结：把"文档修订 + 素材字节"一起钉住

### 2.1 冻结动作

```sh
POST /v1/scenes/emblem/snapshots   {"expectedRevision":1}
```

返回 201 与快照 `snap-00000003`。快照不是引用指针，而是**值拷贝**：

- `document`：冻结那一刻的完整场景文档；
- `assets`：引用闭包里每个素材的完整记录，**含 PNG 字节**。

闭包核对证据（`02-freeze-snap1-closed-asset-meta.json`）：

```json
{
  "assetId": "asset-a",
  "digest": "fce5d44a93777695889c03941c61d7517cce82a1dc766bb2734bd2b353fe3c2d",
  "stateInsideSnapshot": "available",
  "pngBytes": 168,
  "pngSha256": "fce5d44a93777695889c03941c61d7517cce82a1dc766bb2734bd2b353fe3c2d"
}
```

> `pngBytes: 168` 是 JSON 中 base64 字符串的长度；源文件 126 字节经 base64 编码后为 168 字符，
> 解码后的 sha256 与源文件完全一致。

### 2.2 历史隔离的第一次演示：修订场景，快照不变

冻结后把背景改成深色 `#0E2A38` 并提交 revision 2，再读旧快照
（`02-freeze-snap1-digest-unchanged-after-revise.json`）：

```json
{
  "snapshotId": "snap-00000003",
  "digest": "f4802cc460682c8041fe1ae0682d11b2f3ccf0a7ffd89292575294d6432086de",
  "documentBackgroundInsideSnapshot": "#F5F1E8"
}
```

- 快照摘要与冻结时完全相同；
- 快照内文档背景仍是旧的 `#F5F1E8`，新修订进不来。

### 2.3 基准渲染

对冻结快照提交渲染任务（幂等键 `train-render-baseline`），成功后取回结果
（`02-baseline-render.png`）：

| 任务 | 结果 | 输出 |
|---|---|---|
| `job-00000005` attempt 1，succeeded | `png-00000007` | 320x240，6397 字节，sha256 `3583e97c…23bcf` |

渲染器使用的是**任务载荷里的冻结快照**（`job.Payload`），不回查当前素材表。
这是下一章"退役后仍能渲染"的根本原因。

## 小结

1. 素材身份 = ID + 字节摘要；异内容同 ID 在入口就被挡下。
2. 快照捕获的是值（文档 + 素材字节闭包），不是引用；场景后续修订改不动它。
3. 渲染任务把快照再复制进自己的载荷，形成第二道固定输入。

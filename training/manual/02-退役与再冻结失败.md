# 02 退役与再次冻结失败

对应实验脚本第 3、4 段，证据前缀 `03-retire-*`、`04-refreeze-fail-*`。

## 一、退役动作

```sh
POST /v1/assets/asset-a/retire        # 无请求体
→ 200 {"state":"retired"}
```

状态机只有一条边：`available → retired`，没有反向操作，也没有删除接口。
退役是一个**事务内的状态翻转**，并发出 `asset.retired` 领域事件。

### 退役后立刻做的三个尝试

| # | 尝试 | 结果 | 证据 |
|---|---|---|---|
| 1 | 用**相同字节**重新 PUT 同 ID | 409 `asset id already exists` | `reupload-same-content-after-retire-409.json` |
| 2 | 用**不同字节**（asset-b）PUT 同 ID | 409 同上 | `reupload-different-content-after-retire-409.json` |
| 3 | 保存一个仍引用 asset-a 的新场景修订 | 409 `scene references unavailable asset` | `save-revision-referencing-retired-409.json` |

解读：

- 即使字节完全一样，退役 ID 也不能重新激活——退役是终态标记，不是"删除后重建"的空档。
- 场景保存与冻结共用同一条"引用素材必须 available"的事务检查，所以退役会同时封锁新修订和新快照。

## 二、再次冻结为什么必然失败

当前场景在 revision 2，图层 `stamp` 仍引用已退役的 asset-a：

```sh
POST /v1/scenes/emblem/snapshots  {"expectedRevision":2}
→ 409 {"code":"conflict","error":"snapshot references unavailable asset"}
```

证据：`04-refreeze-fail-refreeze-after-retire-409.json`。

冻结的前置条件是"每个引用素材都可用且字节可捕获"。素材退役后这个条件不再成立，
服务在事务内直接拒绝，**不会产生半截快照**。这保证了任何已存在的快照闭包都是自洽的。

## 三、但旧快照照常渲染：历史隔离的核心演示

`snap-00000003` 仍是 `active`，且自带 asset-a 的冻结字节。用新幂等键再渲染一次：

```sh
POST /v1/jobs  {"snapshotId":"snap-00000003","scale":1}
              Idempotency-Key: train-render-after-retire
→ 202 新任务 job-00000009
```

任务成功，输出 `png-00000011`。与退役前基准逐像素比较：

```sh
POST /v1/compare  {"left":"png-00000007","right":"png-00000011"}
→ {"changedPixels":0,"maxDelta":0,"meanDelta":0}
```

两份 PNG 的 sha256 也完全相同（`3583e97c…23bcf`）。原因链条：

1. 冻结时素材字节已被值拷贝进快照；
2. 提交任务时快照又被值拷贝进 `job.Payload`；
3. 执行器只编译 `j.Payload`，**全程不读取当前素材表**。

所以"素材退役"影响的是**未来的冻结与新引用**，不影响**已固定的历史**。

```
时间线：
 rev1 场景 ──冻结──> snap-00000003（含 asset-a 字节）
      │                    │
 rev2 改背景               │  任务1 job-00000005 ──> png-…07（基准）
      │                    │
 asset-a retire ──────────┤  新冻结 ✗ 409（闭包不满足）
      │                    │  新修订 ✗ 409
      │                    └──任务2 job-00000009 ──> png-…11（与基准逐像素相同）
```

## 四、撤回快照与幂等重放（边界补充）

退役演示完成后，把旧快照撤回，观察访问控制的第二层：

| 动作 | 结果 | 证据 |
|---|---|---|
| `POST /snapshots/snap-00000003/revoke` | 200 `{"state":"revoked"}` | `revoke-snap1.json` |
| 用**新**幂等键向撤回快照提交任务 | 409 `snapshot is revoked` | `new-job-on-revoked-409.json` |
| 用**原**幂等键 `train-render-baseline` 重放 | 202，返回的仍是原任务 `job-00000005` | `idempotent-replay-returns-original-job.json` |

两个易错点：

1. **撤回不可恢复**，它封锁的是"新工作"，不删除已经产生的结果。
2. 幂等收据的语义是"快照 ID + 输出倍数"。同键重放即使快照已撤回，也返回原任务而不是报错——
   收据在实例持久状态中全局长期有效。

## 小结

- 退役 = 终态标记，封锁同 ID 重建、封锁新引用、封锁新冻结，但不触碰历史快照。
- 再冻结失败发生在事务校验层，不会留下不完整快照。
- 已冻结快照的渲染只依赖固定载荷，退役前后输出像素一致（`changedPixels=0` + sha256 相同）。
